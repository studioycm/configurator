### Smallest authoring and caching design

Proposed **one `TourDefinition` record per tour and locale**, with stable key, locale, enabled flag, ordered JSON `steps`, integer content revision and normal timestamps. Each step holds a stable key, page identifier, semantic target, title, short description, optional menu/tab/section preparation identifiers and placement preference. Resolve page identifiers through application code to named routes; no record creation is required to demonstrate a step. A simple Filament resource with a reorderable Repeater is enough to edit the list. An enabled switch plus explicit Save is sufficient initially; no separate step table, publishing workflow, revision-history system or progress table is needed.

Keep target/preparation choices in a small code-defined registry exposed as select options. This lets an editor change copy/order and choose existing destinations without editing JavaScript or guessing translated DOM labels. A developer adds new `data-tour` anchors and local reveal handlers when needed. The model manages content, not executable callbacks or application actions. Use the existing admin access convention; no new role system is proposed. Default-locale fallback is sufficient; do not require a translation package.

On ordinary page entry, read enabled definition IDs/revisions for the relevant tour/locale, then deliver that page's ordered steps as JSON with the page. For such a small dataset, one direct JSON read may already be adequate. If caching is desired, use the **existing configured Laravel cache store**, with a key such as `tour-definition:{id}:{revision}` and a bounded TTL (for example one hour). Cache neutral definition data; apply actor-dependent availability when delivering it. No cached per-user step state.

Every content Save updates the steps and increments the revision in the same database transaction. Fresh page entry reads current enabled/revision metadata, so it cannot request the old revision key after a committed change. Disable/delete removes it from the selection query. Old payload keys expire; no broad cache flush, cache tags, queue, new Redis service or cache-pointer invalidation is necessary. This versioned-key approach also avoids an old in-flight read repopulating a forgotten current key. It deliberately retains a small metadata query per page; caching removes repeated payload loading/assembly, not every database read. A small implementation should start uncached if that offers no measured benefit.

An already open tour uses its loaded snapshot until it is restarted or another page loads. Editing content elsewhere does not cause background polling or live interruption. Cross-page continuation stores tour key/revision and next stable step key in browser session state; the destination supplies its current segment. If the content revision changed, restart the destination segment with the current definition rather than interpreting an old array index. Previous/Next/Close never fetch a step or update the model. No tour completion persistence is required.

The fully custom Alpine-popup alternative still saves the JS dependency but makes us own anchoring, viewport collision and accessibility behavior. Retaining Driver as renderer keeps that responsibility smaller; the model/cache choice is independent of the rendering library.

### Local reveal, verification and remaining limits

Keep the earlier accessibility, RTL, focus/Escape, responsive placement, reduced-motion, morph cleanup and re-entry requirements. Same-page navigation and presentation-only reveals remain entirely local. Current editor source still has lazy Groups/Attributes/Rules/Preview components: the first reveal of an unmounted component can legitimately load application content, but it would fail the strict zero-tour-induced-request pilot criterion. Choose already-rendered local targets initially; do not change application loading behavior to make the tour pass. Normal page transitions may load definitions and page data. Preserve existing draft/navigation behavior without adding a second navigation-control system.

The smallest approved future experiment would combine one short manual tour, three semantic targets, one purely local menu/section reveal, and one managed JSON record edited through the simple resource. Verify with network initiators that local steps issue no requests; separately verify one real route transition/resume. Also check that saving/reordering/editing a definition makes the next page entry use the new revision, disable/delete hides it, locale fallback works, and an already open tour remains consistent. Screen-reader/RTL acceptance and real morph behavior are still untested. No package resolution, installation or runtime test ran for this extension.

## Recommendation

Use a small **Alpine controller with Driver.js as its popup/spotlight renderer**, subject to an approved pilot. Keep ordered, translated definitions in code/data, delivered with each page. Alpine owns the active stable step key, preparation, cancellation and page-segment continuation. Driver handles anchoring and popup controls; it does not become the application navigation or state authority. No database, migrations, authoring UI, analytics, accounts or completion service is needed.

Same-page Previous/Next/Close, lookup, positioning and local menu/tab/section reveal must make **zero tour-induced HTTP requests**. Initial definitions and genuine page navigation may use the server. Independent page polling/loading is distinct and must be identified in network evidence. Do not call `$wire`, `Livewire.dispatch` or server actions merely to advance a step.

## Small reusable contract and Filament adapter

Proposed data contract: tour/version/page-segment keys; ordered steps with stable `key`, semantic `target`, short localized `title`/`description`, optional allowlisted local preparation (`menuGroup`, `tab`, `section`), placement preference and missing-target policy. Keep callbacks in trusted adapter code, not arbitrary executable content. Render text safely rather than accepting untrusted HTML.

Use explicit, unique `data-tour="…"` identifiers on owned Blade elements and Filament `extraAttributes()` output. Verify which rendered wrapper receives an attribute before selecting it. Use stable schema keys, not translated labels, array positions, `nth-child`, or styling classes. For vendor-owned sidebar groups, use `NavigationGroup::extraSidebarAttributes()` where verified in the pilot, or one isolated adapter to the installed markup; do not publish/replace the whole sidebar. The installed group view exposes `data-group-label`, which is translated and therefore not a portable target identifier.

Installed Filament sidebar source has `open()`, `groupIsCollapsed()` and `toggleCollapsedGroup()`; `collapsedGroups` starts null and is initialized by the sidebar view. Wait for readiness, expand only when collapsed, and record the prior state. This is an internal-source integration seam, not a promised stable public JS API. Restoration must avoid overwriting changes the user made during the tour. Local section/tab adapters may only change presentation state and must not activate validation, lazy network loading, submit actions or draft reset handlers.

Suggested transition: cancel prior preparation → check available/authorized target → perform allowlisted local reveal → await Alpine next tick and bounded visible-target observation → resolve a fresh DOM node → position/show. Disable repeated transitions while preparing; Close/Escape must still cancel immediately. A session generation token/AbortController prevents a late target from reopening a closed tour. Missing or permission-hidden targets are omitted without revealing restricted copy; an unexpected disappearance gets a short unavailable message with Skip/Close. Never wait indefinitely or retry by clicking arbitrary controls.

Livewire morphs can replace the target node. Keep the overlay outside component morph ownership, re-resolve after updates, and refresh position or safely suspend when the node disappears. The installed 4.4.7 bundle emits `morphed` and **`island.morphed`**; Boost also returned evolving `partial.morphed` documentation. Do not assume that latter name exists in this checkout. A scoped MutationObserver can cover DOM replacement without depending exclusively on internal hooks. Bound/disconnect observers, resize/scroll listeners and timers on every exit.

For genuine cross-page steps, use ordinary authorized navigation and preserve only tour/version/next-step keys in tab-scoped session state. Never store form values or sensitive content. The destination delivers its own ordered segment, checks availability again and resumes after readiness. Consume continuation once; invalidate stale versions. Stop on unrelated navigation. Respect cancelled `livewire:navigate` and existing unsaved/pending guards; never force the transition after a guard refuses. Clean the old renderer during actual page replacement, resume on `livewire:navigated`, and also support full document loads. Global listeners survive SPA navigation, so register once and explicitly remove component-owned listeners. Keep tour step state in the browser throughout.

## Smallest reviewable pilot and validation

Propose one manually started, code-defined tour with three or four steps on one existing read-only page: reveal a collapsed sidebar group, highlight an authorized menu item without navigating, reveal an already-rendered local section/tab, then highlight its content. Choose the page after checking that its reveal controls are purely client-side. Exclude lazy Rules/Preview, record editing, uploads and mutation controls. No automatic first-visit launch or persisted completion. Re-entry restarts cleanly. A later bounded extension can demonstrate one real route transition and destination segment; cross-page behavior is not proven by the same-page pilot.

Acceptance checklist:

1. English/LTR and Hebrew/RTL; meaningful text/button order and explicit Previous/Next labels; visible focus, keyboard-only traversal, Escape/Close from every state, title/description announcements, focus return to a connected launcher or safe fallback. Inspect Driver's dialog semantics and actual screen-reader behavior, not only its ARIA attributes. Tour controls use `type="button"`.
2. Narrow mobile viewport, open/closed drawer, zoom, scroll/resize, long Hebrew text, target near edges, dark mode and reduced motion. Disable animated/smooth movement under reduced motion; use a readable centered fallback if anchoring cannot fit.
3. Missing/forbidden target, slow appearance, target removed/replaced by morph, island update, rapid Next/Previous, Close while waiting, repeated start, initial/full-page load and SPA Back/Forward. No duplicate overlays/listeners or stale reopening.
4. Network capture with request initiators: **zero tour-induced requests** on same-page Previous/Next/Close and local reveals. Distinguish background app traffic; a tab that starts lazy loading fails this pilot criterion. Later cross-page capture must show only justified ordinary page loading and permitted initial definitions, no server-managed step advancement.
5. Existing dirty draft/pending-state guard refuses navigation unchanged. No form submission, save/create, draft discard, authorization bypass, application data write or mutation-triggering simulated click. These checks belong in an approved safe QA context, not in the current research task.

Unknowns before adoption: selected pilot page/semantic target placement, exact mobile drawer interaction, installed-version sidebar adapter resilience, screen-reader/RTL acceptance, Driver behavior under ARI's nested morphs, and safe cross-page continuation through each app's guards. No Composer resolution, package execution or runtime compatibility test was attempted.
