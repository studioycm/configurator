## 2. What item 10 actually refers to

The existing PHP engine has a branch that reads the assembled configuration string. That is where the question came from. It is not necessary for the agreed selected-option-code conditions, and there is no demonstrated current business use that requires retaining it.

| Question | Verified evidence |
| --- | --- |
| Does the engine support reading it? | [ConfiguratorEngine::resolveConditionValue](../../../app/Services/ConfiguratorEngine.php), lines 491–513, recognizes `configuration_code`, `context.*`, `selection_code.*`, and `selection.*`. The assembled-code branch calls `buildConfigurationCode`; an incomplete selection returns null. |
| Can the admin enter it? | [OptionRuleForm](../../../app/Filament/Resources/OptionRules/Schemas/OptionRuleForm.php), lines 29–61, exposes a required **free-text Source**, so the string is technically enterable. There is no dedicated whole-code selector, type validation, or explanation. Its helper instead suggests `configuration.code_set`, which the resolver does not recognize. |
| Can it affect choices? | Any matching rule can intersect allowed options and add hidden/disabled option IDs in [evaluateState](../../../app/Services/ConfiguratorEngine.php), lines 167–244. The demo then repairs an invalid selection. Thus a whole-code condition can indirectly change a selection, but there is no special “rewrite configuration code” action. |
| Is it used by stored rules? | A bounded Boost query selected only rule IDs, active state, trigger/target IDs, priority and `rule_payload.activate_if`. All **5 current rules are active**. Only **2 have conditions**: `context.territory = Europe` and `context.application in [Show All, Wastewater]`. **Zero** use `configuration_code` or `selection_code.*`. This is local evidence only. |
| Is it covered by tests or seeds? | Searches of `tests/` and `database/seeders/` found no condition source using either code branch. Occurrences of `configuration_code` in seeders identify stored POC configuration records, not activation predicates. Existing condition tests cover territory. |

For example, “selected Body Material option has code `Aa`, therefore restrict Seal choices” reads one known source selection. Inspecting an assembled `Aa-Bb-00` string adds an unnecessary parse/position dependency for that case. If the full string includes the target Seal segment, changing Seal can invalidate the condition that changed it: a feedback loop. Code formatting/order should not become an accidental business predicate.

**Recommendation for technical review:** retain typed selected-option identity/code, trusted product-property and Territory/Application inputs. Do not add a whole-code condition editor or whole-code-driven choice changes without a concrete client requirement. The deferred asset mapper can later consume the final code as a result. This preserves agreed scope and explains the legacy branch without promoting it to a requirement.

## 4. Proposed engine boundary for the final plan

These are design recommendations, not new business policies or approved class signatures.

1. Load a coherent definition through Eloquent once per evaluation request: canonical attributes/options, configurator inclusions, stored defaults, UI order, code order, local overrides and rules. Use the current definition on the next evaluation, as E15 requires. A database-free evaluator can then operate on immutable DTOs; do not keep querying models while walking the graph.
2. Allowlist predicate sources and operators through enums/value objects. Sources reference canonical option/attribute IDs or registered product-property keys; selected-option codes are derived strings. Validate operand types, option ownership and the limited group depth. Do not accept SQL, PHP, arbitrary property traversal, or executable expressions from the editor.
3. Represent product/context as input roots. Build attribute dependencies from every selection/applicability read to every state-changing target, including additional conditions, not only a primary trigger. Detect direct and indirect cycles before saving; show the path and relevant rule IDs. UI position and scalar priority do not order dependencies.
4. Evaluate applicability, active constraints and final valid selections in dependency order. Intersect allowed sets, subtract exclusions, preserve an allowed current choice, otherwise restore/default/first-allowed according to the confirmed policy. Retain the latest visitor input when E01 clears a downstream target. A submitted disabled option must not become accepted merely because a client called the action directly.
5. Produce one resolved result containing selections, applicability, allowed/disabled/hidden state, scalar display output, diagnostics, completeness and nullable final code. Preview and public UI consume the same operation. Presentation-only effects do not create choice dependencies unless the contract later allows rules to read their values.
6. Diagnostics should distinguish missing source, inapplicable source, condition mismatch, empty allowed intersection, fallback/restoration, invalid submitted option and scalar-priority tie. Include contributing rule/attribute IDs, with user-facing wording supplied separately. Structural validity is not proof that all possible combinations have legal options.

Acceptance should use small independent expected fixtures for each E00–E16 decision and a few high-value compositions. Run request/Livewire tests for public action validation, authorization and Preview/public parity; test a pure evaluator as pure logic. No new testing dependency is needed to specify these contracts.

## 5. Model and code identity findings

[ConfigProfile](../../../app/Models/ConfigProfile.php) owns attributes and belongs to a ProductProfile. [ConfigAttribute](../../../app/Models/ConfigAttribute.php) belongs to one profile; [ConfigOption](../../../app/Models/ConfigOption.php) contains both code identity and local sort/default state. There is no shared Value entity or configurator-inclusion layer. [CatalogGroup](../../../app/Models/CatalogGroup.php) has a configurator reference, but its adding migration creates an index without a foreign-key constraint. These need coherent replacement, rather than simple class renaming.

Proposed relationships for review: global Attribute + reusable Value → canonical Option; configurator attribute/option inclusion records own local presentation, display order, code order and stored default; Group owns its explicit optional configurator assignment; Product belongs to Group. A canonical `(attribute_id, value_id)` pair is unique, and a canonical option's code is globally unique. Use relational references for options/defaults/mapping membership so removal checks can find affected definitions. Prevent deletion while referenced and require explicit repair; avoid cascades silently removing rules/defaults.

**Verified current MySQL code storage:** `config_options.code` is `varchar(4)`, NOT NULL, `utf8mb4_unicode_ci`, with a nonunique index. Current duplicate groups are `D5`, `DX`, `EP`, `S6`, `S7`, each appearing twice. [ConfigOptionForm](../../../app/Filament/Resources/ConfigOptions/Schemas/ConfigOptionForm.php), lines 32–36, only requires the field. This is not an E14-compliant registry and should not be copied as canonical data.

**Proposed enforcement:** a two-character string column with an explicitly case-sensitive collation and UNIQUE constraint, plus application validation requiring exactly `[A-Za-z0-9]{2}` and an enforced MySQL CHECK. `varchar(2)` with `utf8mb4_0900_bin` is a concrete candidate; retain the wider catalog's normal Unicode text collation separately. Never uppercase, numeric-cast, or generate these manually assigned codes.

Read-only MySQL probes verified that `Aa = aa` is true with the existing collation and false with `utf8mb4_0900_bin`; an explicitly collated ASCII-range regexp accepted `Aa` and `00`, rejected `éA`. An initial literal probe failed because default/connection collations differed; explicit matching collations resolved it. This is a reason to specify collation in the schema/check and test through the actual connection. It is **not** proof of CHECK DDL or concurrent unique-index behavior. The required rehearsal inserts `Aa`, `aa`, `00`, rejects a duplicate `Aa`, and rejects short/long/non-ASCII/whitespace inputs at both relevant boundaries. See [MySQL collation semantics](https://dev.mysql.com/doc/refman/8.0/en/charset-binary-collations.html) and [CHECK constraints](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html).

The approved Product `name` accessor remains a PHP alias of `product_code`; query builders/plugins must explicitly use `product_code`. Do not introduce a physical name column. Product properties retain JSON storage; ordinary core identity indexes and group lookup come first. MySQL indexes selected scalar JSON paths through generated/functional expressions, so add them for measured queries instead of creating indexes for all 67 export columns. [Laravel JSON queries](https://github.com/laravel/docs/blob/13.x/queries.md#json-where-clauses), [MySQL JSON indexes](https://dev.mysql.com/doc/refman/8.0/en/create-table-secondary-indexes.html).

The inspected [User::canAccessPanel](../../../app/Models/User.php) has an explicit two-address allowlist; addresses are intentionally omitted here. Preserve that admission intent and explicitly authorize custom actions/imports. Moving domain models does not authorize replacing admission checks, widening admin access, or inventing a new role hierarchy. The root review also found no application policy classes; specifying the new write boundaries belongs in the final plan.

## 6. Deterministic import contract

The exact column-by-column mapping remains a future implementation specification; these research documents do not deliver it. The following identity/write requirements must be included in that final importer specification.

- Normalize and validate the file before identity resolution. Group `legacy_id` comes from source `group_id`; Product `legacy_id` comes from source `id`. Resolve Product `group_id` to the newly allocated internal Group ID while preserving `legacy_group_id`. Validate one consistent name per legacy group and duplicate/conflicting product identities before writing.
- Define the unique legacy-identity indexes. Current scope is one known legacy source; if another source is introduced, add a source namespace before identities can collide. Do not invent a parent legacy ID or match groups only by display name.
- The import owns an explicit list of core fields and JSON keys. Source-owned blanks overwrite previous values. Missing required columns should fail preflight rather than silently behave like blank cells; this is a proposed failure policy for review. App-only keys survive merges. Missing products survive and are reported. Never use a truthiness filter that drops `0`, `00`, empty-but-intentional source updates or false values.
- Reimport resolves by legacy identity and updates the existing internal record. If a new row's product code conflicts with a different legacy record, report an identity conflict; do not relink or overwrite the other record automatically.
- **MySQL upsert trap:** Laravel's `uniqueBy` argument does not choose the conflict key on MySQL; MySQL uses the table's primary/unique indexes. A future unique product-code index can therefore match the wrong legacy record unless conflicts are checked explicitly. For 501 rows, an import action using explicit identity lookup, validated field merges and model save inside a transaction is a reasonable first implementation. A later bulk upsert must preserve those semantics. [Laravel 13 upserts](https://github.com/laravel/docs/blob/13.x/eloquent.md#upserts).
- Bulk Eloquent upsert does not hydrate/save every model; do not depend on per-model normalization hooks or casts to prepare payloads. Installed `Illuminate/Database/Eloquent/Builder.php:1316` delegates to the base query after adding timestamps/IDs. Prepare JSON serialization deliberately if choosing this path.
- Propose one shared normalization/identity/import action with dry-run and outcome report, usable from CLI and any later admin adapter. Include source hash, map version, row/legacy ID, changed fields and error reasons; do not log unrelated user data. Serialize overlapping imports with an application lock and retain unique constraints as the final race guard. Keep imported-data transactions separate from schema DDL. [Laravel transactions](https://github.com/laravel/docs/blob/13.x/database.md#database-transactions).
- Filament's installed `Importer.php:66–98` runs remap → cast → `resolveRecord()` → validation → fill → save. Identity normalization exclusively in `beforeValidate()` is too late. An adapter must call the shared normalization before resolution and explicitly enforce the intended authorization; merely selecting an import action is not an application-wide policy design.

The authenticated [Laravel Daily upsert tutorial](https://laraveldaily.com/post/upsert-1m-rows-to-laravel-db-5-ways-on-mysql-sqlite-postgresql-benchmarks) was accessible; its page identifies a video and public source repository. The video was not transcribed or its timings independently verified. Its actual [UpsertBenchmark command](https://github.com/LaravelDaily/Laravel-1M-Seeder-Test/blob/26234ac88a8bd597014ac0db94e6198c7ccb921e/app/Console/Commands/UpsertBenchmark.php), inspected through the GitHub connector, compares per-row update-or-create, chunked query/Eloquent upsert and other bulk strategies with explicit update columns and streamed CSV reading. Reuse the separation of parsing, strategy and measurement when scale warrants it; do not run its destructive benchmark commands or import million-row optimizations into this 501-row design.

Proposed migration order: account/infrastructure and retained package dependencies; canonical catalog/configurator definitions; Group hierarchy and explicit configurator assignment; Product identity/core/JSON; configurator inclusion/default/order and rule/mapping relations. Handle any cyclic schema dependency by deferring the relevant FK until both tables exist, not by disabling constraints for the entire build. Use deliberate restrictive deletion semantics for shared definitions and explicit repair operations. The current group-configurator index without an FK is a gap to close.

Remaining concrete blockers before a cutover proposal is executable:

1. Exact table/column retention map, media/archive policy and deployment-environment counts/FKs; this local review did not inspect production.
2. New schema and import-column map, including missing-column behavior, parent-group metadata and global-code constraint DDL.
3. Isolated MySQL rehearsal: fresh migrations, dependency-ordered retained-data transfer, 501-product import, reimport with changed/blank values, collision rejection, app-only preservation and stable internal IDs.
4. Account/login and package-data verification; orphan/morph/file checks for anything retained; auto-increment positions after copying IDs.
5. MySQL checks for the code registry, JSON predicates/selected indexes, FK behavior and concurrency. [phpunit.xml](../../../phpunit.xml) currently selects SQLite `:memory:`; SQLite success cannot establish these behaviors.
6. Matching code/database switch, write-freeze or delta-transfer treatment, job handling, and a rollback that preserves the old database/files/revision. Deploy-on-push is disabled; approval of the strategy is not approval to execute this switch.
