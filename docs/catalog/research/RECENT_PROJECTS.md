## 1. SiteLedger: service boundary transfers; weekly-grid commit semantics do not

[ChangeOrderWorkflowService.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/d0edf866941fbbc99efad0889b79362b75646ee8/v4/full-projects/construction/app/Services/ChangeOrderWorkflowService.php) owns the state transition: it starts a transaction, reloads the root under `lockForUpdate()`, authorizes the actor against the locked record, checks its enum transition map, validates domain references for submission, then updates/logs. Its callback runs within the transaction; repeated target status returns early after authorization. The publisher's shared Filament action delegates to this service rather than reproducing transition logic in a UI callback.

**Transfer:** use the same architectural boundary for a whole Configurator inclusion/rule save: trusted actor + owner, current locked references, validation, then one diff. Our domain validator additionally checks local/canonical IDs, defaults, mapping-set invariants and cycles. Keep the existing panel-admission intent as the gate. The example's construction roles, approval stages, monetary model, activity-log package and second panel are unrelated requirements and are not adopted.

[WeeklyTimesheet.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/d0edf866941fbbc99efad0889b79362b75646ee8/v4/full-projects/construction/app/Filament/Pages/WeeklyTimesheet.php) is useful evidence for a custom grid with two-dimensional state, row/day totals and selective diffs. However, the complete `saveDraft()` iterates cells, validates each and creates/updates/deletes before visiting later cells. It has no enclosing whole-grid transaction in that method. Its validation catch calls `refreshGrid()`, which clears/reloads the state. Therefore a later invalid cell can follow earlier successful writes, and the failure path can replace pending inputs with stored data. This is a source-level inference; the demo was not run or modified.

**Do not transfer:** sequential cell writes or refresh-on-error into the mapping editor. Stage the complete matrix, validate every set before any relationship write, persist once, and retain failed input. The already proposed custom Field/Blade editor is still required; a visually similar grid is not evidence of an equivalent persistence contract.

## 2. Edit-form sidebar: public schema composition, independent lifecycle

[EditTicket.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/7e77668657b58a3f7c285e58eba6450d4e58c1b6/v4/forms/livewire-component-in-editform-sidebar/app/Filament/Resources/Tickets/Pages/EditTicket.php) overrides `content(Schema)` and composes a `Filament\Schemas\Components\Grid`, a Group containing the standard form/relation-manager content, and `Filament\Schemas\Components\Livewire::make('ticket-sidebar')->data(...)`. Its `afterSave()` dispatches a refresh event. This is direct source evidence for composing independently managed content in an existing resource page, without copying a vendor page view.

[TicketSidebar.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/7e77668657b58a3f7c285e58eba6450d4e58c1b6/v4/forms/livewire-component-in-editform-sidebar/app/Livewire/TicketSidebar.php) uses `#[Computed]` for an eager-loaded history query and `#[On]` to reload the record after save. It operates on a persisted record; it does not automatically share the parent form's unsaved fields. Its public `transitionTo()` method in the inspected class does not explicitly authorize the mutation or wrap audit-row creation and record update in a transaction, and `TicketStatus::from()` accepts a raw public-method argument that may throw for an unknown value. This is a bounded inspection of that class, not a claim about every route/policy in the demo.

**Transfer:** the four-tab Configurator can compose owner-scoped managers and a saved-definition Preview using these public schema APIs. Use stable component keys and trusted owner IDs, refresh deliberately after successful saves, and label Preview's saved-data boundary. Recheck our gate and domain scope in every mutation. Do not infer a transaction, record authorization or unsaved form synchronization from `Livewire::make()` or a refresh event.

## 3. Database-driven checkbox columns: matrix rendering evidence only

[ProductsTable.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/9e82df340b564d90cfecf9770009ec7082f61018/v4/tables/dynamic-table-columns-with-database-update/app/Filament/Resources/Products/Tables/ProductsTable.php) builds columns from Country records using `Filament\Tables\Columns\CheckboxColumn`, resolves state from a Product's related country collection, and supplies `updateStateUsing()` that immediately creates or deletes a ProductCountry row. This establishes dynamic columns as a feasible Filament presentation pattern.

**Transfer:** use domain labels/codes to derive headers and membership states. **Do not transfer:** direct create/delete callbacks, a global `Country::all()` analogue for owner-scoped local options, or the demo's bulk deletion. The saved configurator mapping has cross-set source uniqueness, allowed target overlap, references and cycles which cannot be validated by one isolated checkbox. Its selected implementation remains one staged custom Field with one whole-rule Save. The sample resolves to Filament 4 / Livewire 3 and needs v5 namespace/lifecycle review even though the publisher groups it under 4/5.

## 4. External JSON dashboard: normalized result and two verified limits

[EarthquakeFeed.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/2f6c68db859c69da09eed2652e5326b4508b0ecc/v4/full-projects/external-api-dashboard/app/Services/EarthquakeFeed.php) produces one normalized success/unavailable result and memoizes it within the service instance. [AppServiceProvider.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/2f6c68db859c69da09eed2652e5326b4508b0ecc/v4/full-projects/external-api-dashboard/app/Providers/AppServiceProvider.php) registers that service with `$this->app->scoped(...)`. [RecentEarthquakesTable.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/2f6c68db859c69da09eed2652e5326b4508b0ecc/v4/full-projects/external-api-dashboard/app/Filament/Widgets/RecentEarthquakesTable.php) supplies arrays through `Table::records()` and type-hints the action record as an array. These patterns can inform read-only imported-fact/diagnostic presentation without inventing models for every displayed JSON key.

**Pagination limit:** the table returns a bare Collection, then calls `defaultPaginationPageOption(10)->paginated([10])`. That does not establish ten-row slicing for custom data. Filament 5 [custom-data pagination docs](https://filamentphp.com/docs/5.x/tables/custom-data#pagination) require a callback using page/page-size and returning a paginator. Installed `vendor/filament/tables/src/Concerns/HasRecords.php::getTableRecords()` evaluates the custom source, maps records, and returns the collection/paginator; it does not run the Eloquent pagination path on a bare collection. The catalog's Product result query should retain its Eloquent pagination contract; if a fact table uses custom records, supply stable keys and explicit pagination or deliberately display the bounded full set.

**Request-scope limit:** Laravel [scoped bindings](https://github.com/laravel/docs/blob/13.x/container.md#binding-scoped) share one instance within a request/job, not across separate widget requests. Livewire 4 [lazy components are isolated by default](https://livewire.laravel.com/docs/4.x/bundling#lazy-components-are-isolated-by-default). Installed Filament `CanBeLazy` defaults true and Widget supplies lazy properties. Thus this service binding alone cannot guarantee a single fetch or identical snapshot across independently loaded widgets. No network run was performed here; this is a documented lifecycle limit. Our page adapter should own one normalized engine result for its controls/code/diagnostics; unrelated components must not each recompute parts of it from different state.

[EarthquakeFeedTest.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/2f6c68db859c69da09eed2652e5326b4508b0ecc/v4/full-projects/external-api-dashboard/tests/Feature/EarthquakeFeedTest.php) covers normalization, failure/empty results and two calls on one service causing one fake HTTP request. [EarthquakeDashboardTest.php](https://github.com/LaravelDaily/FilamentExamples-Projects/blob/2f6c68db859c69da09eed2652e5326b4508b0ecc/v4/full-projects/external-api-dashboard/tests/Feature/EarthquakeDashboardTest.php) checks page access, expected widgets, stat/chart values and one-row table rendering. The inspected tests do not test >10-row pagination or one shared fetch across independently lazy-loaded widgets. They were read, not executed.

No external API, dashboard, live feed, URL extraction, raw error display or new caching dependency is added to the configurator scope by this example. Product imports remain fixed-source core + three JSON buckets, and literal source data stays inert and escaped.

## Adaptation and bounded follow-through

Boost documentation searches reconfirmed v5 custom array records, array-typed actions, custom pagination and stable record-key requirements; Laravel 13 scoped binding and Livewire 4 lazy isolation. The earlier admin pass already verified `content(Schema)`, schema Livewire composition, custom Fields, authorization, action Halt rollback behavior and relationship-save ordering against installed 5.8.4 source. No new package API or dependency is needed for the recommendations above.

The useful outcome is now concrete: thin Filament adapters over transactional domain saves, independent owner-scoped schema components with explicit saved-state refresh, a staged matrix whose layout may be dynamic, and one runtime result supplying all Preview/public presentation. Required regression cases remain the admin/engine/public annex cases: late aggregate validation causes zero writes; input survives failure; local IDs cannot cross owners; successful reorder preserves defaults; custom-data pagination is real if used; read-only Preview performs no writes. There is sufficient source evidence to proceed to review of those plans without expanding into unrelated projects.
