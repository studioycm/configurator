## 2. Proposed catalog and canonical schema

Table/model names and lengths below are the technical schema selected for the handoff, not newly attributed business decisions. Ordinary IDs are unsigned big integers, with timestamps following project convention. Legacy IDs remain exact strings, not the new primary keys. Nullable legacy IDs permit a genuinely application-authored parent without fabricating a legacy identity. No generic Product field/value tables, stages, visitor configuration records or assets-mapper tables are included.

| --- | --- | --- |

Use explicit primitive fields for known configuration semantics; JSON policy/context metadata has allowlisted keys. Do not expose every policy override initially. The fresh database has no reason to retain POC `is_required`: every applicable included Attribute requires a legal selection. Do not add Product draft/publish/retirement lifecycle states as an incidental schema decision.

**E16 policy resolver:** central typed defaults implement E00–E16. Retain `policy_overrides` as the agreed per-Configurator boundary, with an **initial empty accepted-key allowlist** and no policy toggles. Reject unknown/nonempty override keys rather than merging arbitrary JSON into evaluator settings. Add a named typed key only when its permitted alternative is explicitly specified and covered by tests; do not use this field to enable cycles, optional unanswered Attributes, relaxed restrictions, saved configurations or whole-code feedback. This preserves the override boundary without inventing alternate behavior.

Preserve the working option presentation inputs: [basePresentationState](../../../app/Services/ConfiguratorEngine.php:569) reads default hidden/disabled flags, short labels and hints. The local label override covers the former short label; flags seed the result's hidden/disabled sets before conditional restrictions. The unused `badge()` helper does not justify a badge subsystem. Reuse the existing [ConfigInputType](../../../app/ConfigInputType.php:11) allowlist: `Toggle='toggle'` maps to ToggleButtons and `Select='select'` to Select, as [the demo form](../../../app/Filament/Pages/ConfigEngineDemo.php:311) verifies. Both remain single-choice; no new input types are implied.

For the default-membership invariant, a candidate composite FK is `(configurator_attributes.id, default_configurator_option_id)` → `(configurator_options.configurator_attribute_id, configurator_options.id)`, backed by an explicit composite unique key on the target. Add it after both tables exist. This is proposed DDL to verify on MySQL; Eloquent may still use the ordinary single-ID relation. Foreign keys do not by themselves enforce cross-table Attribute ownership or leaf Group semantics; the save actions validate those under the parent lock.

Validate display/code-order uniqueness across the complete submitted inclusion set before writing. Use stable ID tie-breakers for diagnostics, but reject ambiguous code order as an invalid definition rather than generating a silently rearranged code. Rule priority ties from invalid/imported data remain diagnosed as E08 requires. Reordering must not reassign a default.

**Code CHECK candidate, not executed:** `CHAR_LENGTH(code) = 2` plus a case-sensitive `REGEXP_LIKE` for `^[A-Za-z0-9]{2}$`, with explicit compatible `utf8mb4_0900_bin` collation on subject/pattern. Verify the exact CHECK expression, strict-mode rejection and unique-index behavior in the rehearsal. App validation uses an anchored ASCII expression with no case conversion or whitespace repair. See [MySQL binary collations](https://dev.mysql.com/doc/refman/8.0/en/charset-binary-collations.html), [CHECK constraints](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html).

## 3. Proposed rule association map

Prefer explicit relational membership where removal must find references. The following bounded design avoids JSON arrays of foreign option IDs and does not require a generic expression-language package. It is a technical proposal; the final plan can consolidate classes without weakening the constraints.

| Model/table | Shape and integrity |
| --- | --- |
| `ConfiguratorRule` / `configurator_rules` | `id`, `configurator_id`, `label`, `kind` (`Mapping`/`Advanced`), `is_active`, maintained `priority`; nullable `driver_configurator_attribute_id` and `target_configurator_attribute_id` required for Mapping. No mandatory selected-option trigger for Advanced rules. |
| `RuleConditionGroup` / `rule_condition_groups` | `id`, `rule_id`, `operator` (`All`/`Any`), `sort_order`. Groups are only children of the implicit root AND; there is no parent-group column, so arbitrary nesting is not represented. |
| `RuleCondition` / `rule_conditions` | `id`, `rule_id`, nullable `condition_group_id`, `source_kind`, nullable `source_configurator_attribute_id`, nullable `property_key`/`context_dimension`, `operator`, `operand JSON`. Source-specific validation requires exactly the relevant selector fields. Flat conditions have no group. Composite ownership check prevents assigning a condition to another rule's group. |
| `RuleConditionOption` / `rule_condition_options` | Composite unique `(condition_id, configurator_option_id)`, both FKs. Stores identity/code-selector operands. Code selection in the editor resolves to the included canonical option; the compiler can derive its current code. Product/context operands remain typed scalar/list JSON, with no model IDs hidden inside. |
| `RuleEffect` / `rule_effects` | `id`, `rule_id`, `target_configurator_attribute_id FK`, `kind`, `target_scope` (`Attribute`/`Options`), nullable string `display_value`. Each effect has one target Attribute; several effects allow a rule to affect more than one target. |
| `RuleEffectOption` / `rule_effect_options` | Composite unique `(effect_id, configurator_option_id)`, both FKs. Allow/exclude/hide/disable sets and option-scoped text outcomes refer to included options; domain validation checks target ownership. |
| `MappingSet` / `mapping_sets` | `id`, `rule_id FK`, `label nullable`, `sort_order`. Only Mapping rules can own sets. A complete save requires at least one source and target member in every set. |
| `MappingSetSource` / `mapping_set_sources` | `mapping_set_id`, `rule_id`, `configurator_option_id`; UNIQUE `(rule_id, configurator_option_id)`. Composite FK `(mapping_set_id, rule_id)` ensures that the duplicated rule ID actually owns the set. This enforces at-most-one set per source within a rule. |
| `MappingSetTarget` / `mapping_set_targets` | Composite unique `(mapping_set_id, configurator_option_id)`. Targets may overlap across sets. Validate ownership under the rule's one target Attribute. |

All inclusion/condition/effect/mapping references are scoped to one Configurator. Restrict removal of referenced canonical Options, Values, Attributes and local inclusions until the administrator explicitly repairs the dependencies. A deliberate Rule deletion may cascade its own condition/effect/set rows; this is distinct from deleting a shared Option and silently cascading away rules. FKs cannot enforce nonempty child sets; validate the complete edited aggregate before any write.

Use one transactional definition-save operation: authorize; lock the Configurator; load current references; validate submitted full state, ownership/defaults/order and graph; persist; commit. Canonical deletion/change checks must also coordinate with affected Configurators so a concurrent rule save cannot slip between the reference check and mutation. Lock affected roots in deterministic ID order and keep FK restrictions as the last guard. Filament `mutateFormDataBeforeSave()` is too late if relationship fields already saved; the [admin research](../research/FILAMENT.md) documents that lifecycle.

The catalog write gate must preserve the current `User::canAccessPanel` allowlist intent, through explicit Gate/domain checks and resource authorization. There are no inspected app policy classes to reuse wholesale; no new roles are proposed. Public evaluation only reads definitions and validates interaction input.

## 4. Proposed DTO and operator contract

Use focused PHP classes following the existing `app/Services`/DTO conventions; class names below are proposals. Keep framework loading/persistence outside a database-free evaluator. Do not create an interfaces/repository layer merely to wrap Eloquent.

Proposed implementation paths: `app/Services/ConfiguratorDefinitionLoader.php`, `app/Services/ConfiguratorDefinitionCompiler.php`, and the rebuilt `app/Services/ConfiguratorEngine.php`; immutable objects under the existing singular `app/DTO/` directory (`ConfiguratorDefinition.php`, `ConfiguratorEvaluationInput.php`, `ConfiguratorEvaluationResult.php`, `ConfiguratorRuleDTO.php`, `ConfiguratorConditionDTO.php`, `ConfiguratorEffectDTO.php`). Focused writes use `app/Actions/SaveConfiguratorDefinition.php` and `app/Actions/ImportCatalogProducts.php`; the CLI adapter is `app/Console/Commands/ImportCatalogProducts.php`. Parser/normalization belongs in `app/Services/CatalogImportParser.php`, with one explicit raw/canonical mode. These are proposed files, not files created by this evaluation.

| Boundary | Proposed contents / operation |
| --- | --- |
| Definition loader/compiler | Load current Product → Group → optional Configurator and all inclusions/rules once per request; validate and compile immutable `ConfiguratorDefinition` with maps keyed by local association IDs and canonical option IDs/codes. Include default/UI/code orders and dependency adjacency. No POC stages or first saved configuration lookup. |
| `ConfiguratorEvaluationInput` | Trusted Product property map and trusted assigned definition; validated single Territory/Application values; prior selected ConfiguratorOption IDs keyed by ConfiguratorAttribute ID; remembered valid choices for temporarily hidden Attributes; one interaction intent. Client counts, allowed lists, code or Product facts are never trusted inputs. |
| Interaction intent | `Initialize`, `SelectOption(configuratorAttributeId, configuratorOptionId)`, `ChangeContext(dimension, choice)` or `Reevaluate`. These are operation kinds, not persisted workflow records. |
| `ConfiguratorConditionDTO` | Source enum, source selector, operator enum, correctly typed scalar/list or referenced option operand; group membership compiled to root `All` containing predicates or one-level `All`/`Any` groups. |
| `ConfiguratorRuleDTO` | Identity, active flag, priority, condition group; either Mapping driver/target/sets or typed effects. Inactive rules do not contribute to evaluation. |
| `ConfiguratorEvaluationResult` | Applicable attributes; legal, hidden and disabled options; accepted selections and remembered choices; separate label/display-value/hint results; diagnostics with rule/attribute IDs; `isComplete`; nullable hyphen-separated `configurationCode`. Product code remains independent. |

**Allowlisted sources:** `SelectionOption`, `SelectionCode`, registered `ProductProperty`, `Territory`, `Application`. A selected-code operand is authored by selecting an included canonical option and displaying its exact code; it is not a free-form PHP/SQL/path expression. Missing/inapplicable selection is a tagged state, never zero, empty string or a synthetic Option. The assembled `configuration_code` branch stays outside this initial contract because no current business use was demonstrated. Do not silently drop an approved selected-option-code condition with it.

**Proposed first operators:** `Equals`, `NotEquals`, `In`, `NotIn`; all use strict typed comparison and case-preserving strings. For SelectionOption/SelectionCode, operands reference options of the named source Attribute; list operators require nonempty homogeneous lists. `Contains` can preserve the legacy string capability only for registered text Product properties, with literal case-sensitive substring semantics; it does not execute regex or split a comma-delimited string. No numerical comparison of human strings such as `6 bar (90 psi)`, `1/8″` or `60°C (140°F)`. Numeric operators require a later explicitly typed property contract, not an implicit cast.

Missing/inapplicable selection makes its predicate false for all four comparisons, including negatives. Missing Product key/JSON null likewise does not accidentally satisfy a negative comparison; a present empty source string remains a distinct value under the import map. `All` is an explicit unrestricted context state: predicates specific to that dimension do not match it, including negative predicates. Another valid branch of an `Any` group can still activate the rule. Empty nested groups reject save; an empty root condition list means an unconditional rule. These edge semantics must appear in independent fixtures before implementation is accepted.

**Typed effects:** `AllowOptions`, `ExcludeOptions`, `HideOptions`, `DisableOptions`, `HideAttribute`, `SetLabel`, `SetDisplayValue`, `SetHint`. Mapping restrictions always disable outside options. Hiding a whole Attribute changes applicability; hiding an Option only removes that Option. Matching HideAttribute effects combine to hide; the initial contract does not add a higher-priority “unhide and override constraints” effect. Scalar text outcomes use E08 priority and never change code identity or selection.

## 5. Deterministic DAG evaluation and input lifecycle

1. **Compile structural dependencies before persistence.** For every effect that changes legal choices or Attribute applicability, add an edge from every selection Attribute read by its conditions to its target Attribute. Include the mapping driver and all additional selection conditions, including reads inside OR groups. Product/context inputs are roots. Detect self-edges and indirect cycles and return the Attribute/rule path. Conservatively validate the stored definition including inactive rules, so activation cannot expose an unvalidated cycle; runtime still skips inactive rules. This is a proposed structural-validation choice, not a claim the old engine does it.
2. **Keep presentation evaluation separate.** Label/display-value/hint effects run after choices settle and cannot be read by predicates. A rule reading A to change A's label creates no choice-feedback dependency. A rule reading A to hide A does create one and is rejected. This distinction prevents both accidental cycles and over-restricting harmless presentation rules.
3. **Refresh before accepting a command.** On each action, load the current Product/group assignment/definition and reconcile prior state under it. If no Configurator is assigned, return an explicit unavailable state with no generated configuration code, keeping the Product page valid. If the assignment changed, discard foreign local association IDs and initialize the new definition; do not reuse IDs from the old definition as if they meant the same thing.
4. **Validate submitted selections against that current result.** The named Attribute must be applicable and the Option included and legal. Reject a forged/stale disabled or hidden option with a bounded diagnostic and refreshed state. Do not clear upstream choices to make the submitted option legal. For a valid selection or context change, apply that intent, then run the complete evaluation below; preserve the accepted latest intent when downstream restrictions conflict.
5. **Walk Attributes in topological order.** Stable ID breaks ties between independent nodes; UI/code order never controls graph evaluation. Evaluate incoming applicability/constraint effects using already-settled source selections. If inapplicable, remember a prior valid choice, clear active selection and skip its code/outgoing selection contribution. Otherwise start from included options minus local `hidden_by_default`/`disabled_by_default` options, seed those presentation sets, intersect each active allow/mapping set and subtract conditional exclusions, hidden and disabled options. An unmapped driver adds no restriction; missing driver makes its mapping inactive.
6. **Resolve each applicable selection once its incoming state is known.** Preserve a legal current selection. On becoming applicable, prefer the remembered choice if legal, then the stored default if legal, then first legal option by local display order with stable ID tie-breaker. If none is legal, clear that target and report contributing rules; no invented option or relaxation. A downstream condition requiring the now-missing choice is nonmatching under E00, while unrelated rules continue. The complete configuration is nevertheless incomplete.
7. **Apply scalar presentation effects to the settled state.** Highest priority wins per target/output field. Conflicting equal-priority scalar values produce a diagnostic. Proposed deterministic degraded behavior is to retain the base/local presentation for the tied field rather than silently using the later row ID; constraints remain unaffected. This tie-display fallback is an implementation recommendation for review.
8. **Derive completeness and code from this one result.** Every applicable included Attribute must have a legal selection; structural definition errors also withhold code. An empty/unusable Configurator must not generate an empty string as a valid code. Sort only applicable Attributes by configurator-local code order, join their canonical two-character codes with `-`, and expose no final code when incomplete. Both public UI and Preview consume this result unchanged.

A finite acyclic choice graph therefore settles in dependency order without an arbitrary two-pass or retry-until-stable loop. [The current demo](../../../app/Filament/Pages/ConfigEngineDemo.php:482) evaluates twice but repairs only between evaluations; [current code generation](../../../app/Services/ConfiguratorEngine.php:388) does not receive final legal/applicable state. This is the concrete defect the proposed boundary replaces. [Legacy predicate matching](../../../app/Services/ConfiguratorEngine.php:546) uses loose comparisons and has no missing-state guard; its tests do not establish the new semantics.

Current definitions need a coherent read across their several tables. Proposed loader boundary: one short database read transaction with a verified consistent snapshot, or another explicit coherence mechanism if connection isolation differs. Do not claim that eager loading alone makes separate queries atomic. Definitions are not pinned across visitor requests, and no historical version store is added. Clear request-local caches on the next request; never retain an old compiled definition indefinitely.

## 7. Proposed import operation and failure boundary

For this source, propose one CLI-first shared import action; an eventual admin adapter calls the same contract. This is not approval for a job/import framework or a new dependency.

1. Parse and normalize without writes. Check the expected header/map version, 501-row starter expectation where applicable, all identities, duplicate/conflicting Product codes, consistent Group names and explicitly supplied parent metadata. A later legitimate file can have another count; 501 is a starter fixture assertion, not a universal schema rule.
2. Build a dry-run plan of Group/Product creates/updates, changed source-owned keys, unchanged rows and absent source Products. Compare existing records by legacy identity, not code/name. Product-code conflicts with another legacy record are errors, not permission to relink. Absence reporting is scoped to the source/Groups represented by the import, not unrelated catalog records.
3. Apply only that exact source/map and normalized parent metadata after authorization. Require the three SHA-256 values from the same dry-run, including a parent-metadata hash for an empty map; changing, adding or removing metadata invalidates that approval. Acquire one import lock supported by the configured cache store; use one transaction for Group creation/resolution and all Product writes. Recheck identity conflicts under database constraints/locks. A failed row/constraint rolls back this entire file; report the failure, not partial success. This full-file atomicity is a technical proposal for the initial 501 rows.
4. For each row, update only the owned core fields and listed JSON keys. Write intentional blanks. Preserve internal IDs, app-only fields and JSON keys. New Group parent/configurator/filter metadata comes only from explicit import/admin metadata, never overwritten by an absent source column on reimport.
5. Record a bounded private outcome artifact with source/map hashes, normalization/map version, normalized parent metadata and its hash, totals, source row and legacy/internal IDs, changed fields and error reasons. Tie dry-run/apply to those exact three hashes; revalidate if the database changed between them. Avoid a new import-history UI/table until actually required.

Use model writes with prepared casts for the first 501 rows. MySQL upsert does not honor Laravel `uniqueBy` as an exclusive conflict key, so a bulk shortcut can overwrite the wrong identity if other unique indexes conflict. See [Laravel upserts](https://github.com/laravel/docs/blob/13.x/eloquent.md#upserts), [array casts](https://github.com/laravel/docs/blob/13.x/eloquent-mutators.md#array-and-json-casting), [transactions](https://github.com/laravel/docs/blob/13.x/database.md#database-transactions), [pessimistic locks](https://github.com/laravel/docs/blob/13.x/queries.md#pessimistic-locking). Boost reconfirmed these version-scoped APIs for this evaluation.

The installed Filament importer resolves a record before its validation hook, and its row/job lifecycle does not itself deliver this whole-file transaction. Do not normalize identity only in `beforeValidate()`, use `ignoreBlankState()` for source-owned fields, or let per-row partial success silently replace the selected operation. Custom import actions must enforce the same catalog write gate.
